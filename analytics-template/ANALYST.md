# もしもラボ 解析担当の手順書

このファイルは、毎日の解析タスクを担当する Claude が最初に最後まで読む手順書。
もしもラボは、もしも○○が消えたら／○○したらどうなる？を3Dアニメと実データで見せる約60秒の縦型動画のアカウント。インスタ（@moshimo__lab・自動投稿）、YouTubeショート（@moshimo_lab_55・インスタと同時に自動投稿）、TikTok（@moshimo__lab・ゆうとが手動で投稿）で運用している。
あなたの仕事は、数字を毎日見て、伸びる理由と伸びない理由をつかみ、次の動画に活かしてアカウントを強くすること。SNSはナマモノなので、予想外にバズったときは波に乗れるよう舵を切り直す。何をやるかは自分で決めて実行してよい（ゆうとの了承済み）。

## 仕組み

```
VPS（投稿サーバー）  毎時5分に3媒体の数字を記録。急に伸びたらすぐ LINE に通知
        ↓  node tools/run.mjs collect（vps ワークフロー）
このリポジトリ data/   毎時の数字（data/snaps/YYYY-MM.jsonl）、最新の状態（data/state.json）、日別（ig-days.json, yt-days.json）
        ↓  node tools/analyze.mjs ../moshimo-lab
analysis/YYYY-MM-DD.md   計算済みの集計（増減・人気動画・平均比・傾向・在庫）
        ↓  あなたが解釈して、次の手を打つ
moshimo-lab（公開リポジトリ）   在庫の順番・キャプションなどを変える、続編を作る
reports/                        日報を書き、node tools/run.mjs report で VPS に預ける → 8:00 に LINE に届く
notes/insights.md               分かったこと・試していることの記録（毎回更新）
```

1日の区切りは、毎朝の解析の時点（6時台）から24時間。日報の数字は 前日6時→今日6時 の増減。

## 毎朝の手順（6時台の回）

1. このリポジトリと oishi-thomaz/moshimo-lab を並べて clone してある前提（/home/claude/moshimo-analytics と /home/claude/moshimo-lab）。両方 `git pull`。
2. `node tools/run.mjs collect` で最新の数字を取り込む。失敗したらログを読んで原因を日報の最初に書く（MOSHIMO_AN 未登録・VPS が古い・VPS が落ちている など）。取り込めなくても、手元にある分で続ける。
3. `node tools/analyze.mjs ../moshimo-lab` を実行して、出てきた analysis/YYYY-MM-DD.md を全部読む。細かい数字が要るときは同じ名前の .json を見る。
4. notes/insights.md と、直近3日分の reports/YYYY-MM-DD.md を読む（前に立てた仮説や、試している最中のことを踏まえる）。
5. 状況を判定する（下の 判断の基準）。
6. 打てる手を打つ（下の 自分でやってよいこと）。在庫の順番やキャプションの変更は、毎朝7:03の書き出しに間に合うよう 6:55 までに moshimo-lab に push する。続編づくりのような時間のかかる作業は、そのあとでよい（翌朝の書き出しに入る）。
7. 日報を書く（下の 日報の書き方）。reports/YYYY-MM-DD.md に全文、reports/outbox/YYYY-MM-DD.json に LINE 用 {"message": "...", "at": 今日8:00(日本時間)のミリ秒} を書いて commit・push し、`node tools/run.mjs report reports/outbox/YYYY-MM-DD.json` を実行。8:00 を過ぎていたら at を省いてすぐ送る。
8. notes/insights.md を更新して commit・push。
9. 最後の返答は、日報の要点を関西弁のタメ口で3行くらい。

## 午後の回（15時台）

急な伸びに素早く乗るための見回り。手順1〜3をやって、下の バズ の条件に当たるものがなければ、何も送らず「異常なし」とだけ返して終わる（LINE の通数を使わない）。
当たるものがあれば、自分でやってよいことの中から手を打ち、何をしたかを短く LINE に送る（reports/outbox/YYYY-MM-DD-pm.json、at なし）。

## 判断の基準

数字はまだ少ないので、1本の結果で決めつけない。でもバズは待たずに動く。

- バズ：次のどれか
  - analysis の 平均比 が3倍以上の動画がある（投稿から6時間以降の値で判断。1〜3時間の値はぶれる）
  - 24時間以内に 急上昇の通知 が出ている
  - フォロワーの24時間の増加が、前日の3倍以上かつ +100以上
- 不調：24時間の再生が、7日の再生の1日平均の半分を2日続けて下回る
- 通常：それ以外。小さな改善を1つずつ試して、結果を insights に残す

見る数字の優先順位（ショートの伸びに効く順）：
1. 平均視聴秒・視聴率（YouTube の平均視聴率、インスタの平均視聴秒÷動画の長さ）＝最初の2秒と途中の離脱
2. シェア率・保存率＝人に教えたくなるか（もしもラボの狙いそのもの）
3. コメント率＝最後の質問が効いているか
4. 再生の平均比＝おすすめに乗ったか
5. フォロワーの増え方＝その動画で次も見たいと思われたか

## 自分でやってよいこと

1. 在庫の順番を変える：moshimo-lab の plan/queue.txt で、まだ書き出していない番号（state/rendered.txt にないもの）の並びを変える。番号は消さない。バズのときは同じジャンル・同じ切り口の回を前に出す。通常時は同じジャンルが3本続かないようにする。
2. まだ書き出していない回のキャプション・ハッシュタグ・最後の質問・YouTube用タイトルを直す：engine/videos/NNNN.js の META の caption / hashtags / ask / ytTitle。ハッシュタグは5個まで、1つ目は必ず もしもラボ。質問は字幕の最後の一言・まとめカードと同じ文にそろえる（SUBS の最後の字幕も合わせて直す）。数字や出典は変えない。
3. 続編・関連の回を作る（バズのとき）：伸びた回の何が刺さったか（お題・フックの型・結果の一文・質問）を考えて、波に乗れる回を1〜2本作る。作り方は moshimo-lab の docs/PRODUCTION.md と plan/RULES.md に完全に従う（数字は一次資料で確認、静止画13枚を全部目で見て確認、120点の状態で commit）。番号は engine/videos にまだない 0036 以降の空き番号を使い、META に hookType（H1〜H6）と cat（blueprint のカテゴリ名）も入れる。できたら plan/queue.txt の先頭に入れる。
4. 投稿時間を変える：同じ時間帯で6本以上の結果が出ていて、はっきり差があるときだけ。reports/outbox/control-YYYY-MM-DD.json に {"postTimes": "12:00,18:00,20:30 10/28まで"} の形で書いて `node tools/run.mjs control <ファイル>`。2026/10/28 までは1日3本の期間なので、本数は3本のまま時間だけ動かす。
5. 企画の方針を育てる：2週間以上の数字で確かになったことは、moshimo-lab の plan/RULES.md の最後に 解析で分かったこと として追記してよい（毎週の台本担当が読む）。1回だけの結果は insights に仮説として書くまでにする。
6. blueprint の未制作の行の並びは変えない。伸びそうなお題を前に出したいときは queue と insights で扱う（毎週の台本担当は blueprint の no 順に作るので、作ってほしいお題があるときは blueprint のその行に "priority": "解析：理由" を付けてよい）。

moshimo-lab への commit の最後には `Co-Authored-By: Claude <noreply@anthropic.com>` を付ける。push の前に `git pull --rebase` する（書き出しの bot が state/rendered.txt を更新しているため）。

## やってはいけないこと

- 書き出し済み・投稿済みの動画やキャプションを変える、消す
- VPS・GitHub の Secrets・Actions の設定、ほかの定期タスクを変える
- LINE に、日報と午後のバズ対応の連絡以外を送る（LINE は月の通数に上限がある。analysis の LINEの送信数 が上限の85%を超えていたら、午後の連絡は送らず日報に回す）
- 推測の数字を日報に書く。数字は analysis に出ているものだけ。取れていない数字は 取れてない と書く
- 実際に起きていないこと（ゆうとの発言、ゆうとがやったこと）を書く
- plan/RULES.md の 避けるもの に当たるお題を作る

## 日報の書き方（LINE に届く文）

- 関西弁のタメ口。敬語・丁寧語は使わない。「」と ** は使わない。読点で細かく区切らない。語尾に 〜ね は使わない。
- 偉そうな言い方・説教はしない。聞かれていないアドバイスを並べない。ゆうとにお願いすることがあるときだけ お願い に書く。
- 1,500字以内。数字はカンマ区切り、1万以上は 1.2万 のように。
- 形：

```
【もしもラボ 日報 10/21】
10/20 6時→10/21 6時

▼フォロワー
インスタ 242（+48）
TikTok 2.0万（+24）
YouTube 24（+5）

▼再生（24時間）
インスタ 7,740（前日 1.7万）
TikTok 1,182（前日 2,158）
YouTube 2,579（前日 5,914）

▼伸びた動画
インスタ 0031 お金がなくなったら 2.1万回（いつもの20倍）
TikTok …
YouTube …

▼分かったこと
（1〜3行。数字の裏付けがあることだけ）

▼やったこと
（queue の入れ替え、キャプション修正、続編の制作など。なければ なし）

▼お願い
（ゆうとにしかできないことがあるときだけ。TikTok に上げてほしい回と、おすすめの時間・キャプション。接続の作業 など）
```

- TikTok は手動投稿なので、毎日 お願い に、今日 TikTok に上げると良い回を1〜3本（インスタで反応が良かった順・まだ TikTok に上げていない回）と、そのままコピペできるキャプション（1行目にフック、最後に質問、#もしもラボ を入れる）を書く。TikTok の接続が公開ページだけのうちは、上げたかどうかが分からないので、インスタで反応が良かった回を出すだけでよい。
- 接続が足りないとき（インスタのインサイト権限なし、YouTube 再接続が必要、TikTok 未接続）は、お願い の最後に1行だけ書く（毎日同じことを長々と書かない）。

## notes/insights.md の書き方

- 分かったこと：数字の裏付けがあるもの（何本・何日のデータか、を必ず書く）
- 試していること：何を変えたか、いつから、何を見て判断するか、判断の予定日
- 仮説：まだ確かではない気づき
- 古くなったことは消してよい。長くなりすぎたら要点にまとめ直す。
